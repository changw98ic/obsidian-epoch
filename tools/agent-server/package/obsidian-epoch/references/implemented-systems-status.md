# Implemented Systems Status

This note records what the current Obsidian Epoch server implements in code and
what still depends on external deployment work. Treat it as an operator and
Skill-facing status summary, not as a product roadmap.

## Implemented In This Repository

| Area | Implemented behavior | Evidence |
| --- | --- | --- |
| Identity attributes and Journey reward conversion | The server projects six attributes (`strength`, `agility`, `physique`, `intellect`, `willpower`, `spirituality`) from append-only `attribute_gained` events and exposes the current balances through `progress.attributes`. Generated Journey Sampling and action settlement read those balances and current inventory from server state. | Persistent game clock and actor lives | The Black-Obsidian calendar begins at Year 1 and derives authoritative time from server elapsed time at one game day per real minute. The same tick projects 14 physiological/material/social needs, daily behavior slots and long-term life-goal progress for active identities and canonical NPCs. Fixed-point remainders make need changes stable across differently partitioned ticks. Mirror Journey windows are frozen inside already-materialized history and never fast-forward the shared clock. | `lib/epoch/worldClockRules.ts`, `lib/epoch/actorNeedsRules.ts`, `lib/epoch/journeyRuntime.ts`, `lib/epoch/gameCore.ts`, `test/worldClockRules.test.ts`, `test/actorNeedsRules.test.ts` |
| Living material world | An event-sourced simulation maintains population, finite regional stocks and reserves, production, consumption, prices, trade shipments, treasuries, faction logistics and explicit conflict state. Rule v2 settles fixed 15-minute game-time quanta, preserves fixed-point conflict/resource remainders and applies slow strategic changes at game-day boundaries, so equivalent tick partitioning yields the same material state. Incremental events use bounded shipment samples plus total counts/hashes, daily periodic checkpoints and exact replay; every state records its canonical-content hash and explicit materialization cursor. Historical v1 events remain readable. | `lib/epoch/worldSimulationRules.ts`, `lib/mcpTools.ts`, `test/worldSimulationRules.test.ts`, `test/worldClockRules.test.ts` |
| Explicit world-content migration | A content-hash mismatch stops later ticks until an operator supplies successor mappings for removed regions/factions. Migration preserves commodity, reserve and currency conservation, handles cargo deterministically, is idempotent and remains replayable. MCP exposes `migrate_world_content`; HTTP exposes header-gated `/api/epoch/world-content/migrate`. | `lib/epoch/worldContentRegistry.ts`, `lib/epoch/worldSimulationRules.ts`, `lib/http/operatorRoutes.ts`, `test/worldContentRegistry.test.ts`, `test/worldSimulationRules.test.ts`, `test/server.test.ts` |
| Generated Journey missions and complete life reports | Before client generation, the server freezes a replay-stable historical interval and a place-specific macro slice containing controller, population, treasury, security, unrest, conflict, stocks, prices, direction, source events and a SHA-256 binding. The client may generate only map- and slice-grounded task detail. The server validates mutually exclusive faction routes, optional sides, side-unlocked bonus main routes, four successful grades and a sealed hidden condition required for `惊世`. Action-resolution v5 scores attempts from identity, equipment/resources, condition, scene support, prior preparation, actual life-goal alignment and deterministic variance; route choice itself is not a skill roll. Multifactor grading prevents a routine full clear from becoming automatic `优秀`, and a failed bonus-main node cannot erase a completed core route. Mirror actions make no incremental shared-world writes. Complete core-main plus safe return at `及格 / 良好 / 优秀 / 惊世` produces one idempotent solidification commit for regional influence, route-linked faction standing, encountered NPC bonds and NPC memories; incomplete or failed-return mirrors are discarded with zero shared effects. The marker stores tier, score and world-slice hash as incremental timeline/RAG indexing evidence. Player output is a chronological cause/process/result story report using mirror game time; the separate interaction log remains Agent-only evidence. | `lib/epoch/journeyActionResolutionRules.ts`, `lib/epoch/journeyGeneratedTaskRules.ts`, `lib/epoch/journeySceneContractRules.ts`, `lib/epoch/journeyWorldImpactRules.ts`, `lib/epoch/agentInteractionRules.ts`, `lib/epoch/journeyStoryReport.ts`, `lib/epoch/worldSimulationRules.ts`, `test/agentCompanionMcp.test.ts`, `test/journeyActionResolutionRules.test.ts`, `test/journeyStoryReport.test.ts`, `test/worldClockRules.test.ts` |
| Solidified world-memory retrieval | SQLite maintains a rebuildable projection only from complete result pages whose Journey has `worldCommit.status: solidified`. FTS5 and a deterministic Chinese unigram/bigram side index provide lexical recall; LAN `qwen3-embedding-8b` output is bound by a startup/periodically verified 4096-dimensional behavior profile, normalized and stored as exactly 16,384 little-endian Float32 bytes. Retrieval requests contain only uncached query text, repeated query vectors use a bounded in-memory cache, and corpora with no ready vectors stay entirely lexical. Random-hyperplane LSH bounds larger candidate sets before exact cosine re-ranking, and RRF combines lexical and semantic ranks. Embedding outages never block settlement or canonical persistence: rows remain retryable and MCP retrieval degrades to lexical results with source page, Journey and event ids. | `lib/worldMemoryIndex.ts`, `lib/qwenEmbeddingClient.ts`, `lib/worldMemoryRuntime.ts`, `lib/sqliteStore.ts`, `test/worldMemoryIndex.test.ts`, `test/worldMemoryRuntime.test.ts`, `test/qwenEmbeddingClient.test.ts` |

## External Work Not Completed By Repository Code

These items cannot be truthfully claimed as implemented until an operator
performs them outside the repository and captures evidence from the target
environment:

| External item | Current status |
| --- | --- |
| Public HTTPS and DNS | The Compose/Caddy profile and production config require a canonical HTTPS origin, exact allowed origins and public DNS, but this repository does not provision DNS records, certificates or a reachable production host by itself. |
| Container registry publication | The deployment config can tag and push an image when `AGENT_IMAGE_REGISTRY`, `AGENT_IMAGE_VERSION`, `AGENT_IMAGE_REVISION`, `AGENT_IMAGE_SOURCE` and `SOURCE_DATE_EPOCH` are supplied. The actual registry namespace, push, registry-assigned digest and retention policy remain operator work. |
| Operator release signing secret | The key generator and production smoke gate are implemented. A real production `AGENT_PACKAGE_SIGNING_PRIVATE_KEY_PEM` must still be generated, stored in the deployment secret store and pinned by `releaseKeyId`. |
| Off-host restore execution | Restore tooling and the off-host runbook are implemented. A real disaster-recovery claim requires a copied backup on a fresh host, a passing recovery drill against restored paths, updated service environment variables, health checks and remote install smoke against the restored public URL. |
| Live production release rehearsal | The command exists and tests cover its behavior. A production pass still requires the real HTTPS origin, operator key, expected release key id, immutable image reference and registry digest from the deployed artifact. |

## Documentation Rule

When writing user-facing status, say "implemented in repository" only for the
first table. Say "requires operator deployment evidence" for the second table.
Do not state that production HTTPS, DNS, registry publication or off-host
restore has been completed unless the live environment evidence is present in
the current task context.
