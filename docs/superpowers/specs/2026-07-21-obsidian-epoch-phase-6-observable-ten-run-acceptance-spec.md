## 1. 阶段定位

Phase 0 至 Phase 5 已经定义了事件底座、世界演进、角色成长、Roguelite 局内外循环以及生产和市场方向。Phase 6 不再扩写新的大系统，而是把已有系统接成一个可重复、可审计、可量化的真实对局闭环。

当前十局外部模型游玩已经证明正式 MCP 路径可以连续执行，但还没有证明玩家资源、技能、修行、多维面板、RAG、世界状态和结算评分形成了可信的数值闭环。本阶段负责消除这一验收盲区。

### 1.1 当前基线

| 观察项 | 当前证据 | Phase 6 要求 |
|---|---:|---:|
| 正式旅程启动 | 10 次 | 10 次均有完整结算回执 |
| 旧版工具调用 | 0 次 | 持续为 0 |
| `player_panel` 错误 | 1 次 | 0 次 |
| 结果页读取 | 0 次 | 每局至少 1 次，共 10 次 |
| 可见评分 | 多局重复为 94 / 良好 | 由评分分项真实计算并可解释 |
| 仓库和资源变化 | 未形成逐局证据 | 每局有前后快照、净变化和事件来源 |
| 技能和修行变化 | 未形成逐局证据 | 每局明确变化或明确无变化原因 |
| RAG 面板变化 | 未形成逐局证据 | 每局有投影变化和 canonical event 引用 |
| 世界演进变化 | 未形成逐局证据 | 每局有世界切片差异或合法无变化原因 |

该基线只用于定义缺口，不能计入 Phase 6 完成度。

## 2. 规范性目标

### G1：逐局真实回执

每局必须产生唯一、不可变、可重放的 `RunReceipt`。回执必须同时覆盖玩家、仓库、资源、成长、RAG、世界、评分和事件链。

### G2：数值来源唯一

所有持久变化必须由 canonical event ledger 推导。MCP 返回、RAG 文档、模型叙述、前端缓存和测试报告都不得成为第二权威源。

### G3：评分与战斗力解耦

任务评分衡量执行质量，战斗适配度衡量角色构筑与当前遭遇的匹配程度。不得引入单一全局战斗力，也不得用任务强度直接赠送基础属性。

### G4：十局可重复验收

同一实验配置必须能够连续运行十局，得到机器可读的逐局记录、汇总指标、失败原因和审计关联。

### G5：进度证据化

项目进度只由机器可读进度账本计算。聊天结论、手工百分比、代码存在、测试曾经通过都不能单独算作“已验证”。

### G6：问题可以定位到事件

任何资源异常、属性异常、评分异常、RAG 异常和世界异常都必须能够从回执追溯到事件 ID、规则版本、目录版本和随机种子。

---

## 3. 非目标

本阶段不新增第二套角色属性模型。

本阶段不以更多文本内容、世界数量或装备数量代替闭环验收。

本阶段不引入全局综合战斗力数值。

本阶段不让 Claude、GLM 或其他宿主模型直接写入持久状态。

本阶段不把 RAG 面板变成数据库或规则裁判。

本阶段不以 mock、fixture、snapshot 或伪造模型响应证明真实 MCP 链路完成。

---

## 4. 不可违反的系统约束

1. canonical event ledger 是所有持久状态的唯一权威源。
2. 任何结算写入必须满足幂等性，同一 `receiptId` 只能提交一次。
3. RAG 只投影、检索和摘要，不得反向覆盖 canonical state。
4. 基础属性只能通过明确的成长事件、消耗和规则获得，不能因低、中、高强度自动增长。
5. 任务评分不能读取全局战斗力，因为系统不存在该值。
6. 遭遇结果可以读取十维适配向量，但评分只读取执行过程和目标完成情况。
7. 所有随机过程必须记录 `seed`、规则版本和目录版本。
8. 世界推进必须由服务端时钟和 canonical action 触发，模型叙述不能推进世界。
9. 任一面板读取失败都必须使该局验收失败，不能静默填充默认值。
10. 日志、回执和证据不得包含恢复码、operator key、API key、访问令牌或完整认证头。

        |
        v

        |
        +--------------------+--------------------+
        |                    |                    |

        +--------------------+--------------------+
                             |

## 6. `RunReceipt` 合约

每一局必须生成一个 `RunReceipt`。字段可以扩展，但下列语义不可删除。

| 字段 | 必需 | 语义 |
|---|---:|---|
| `schemaVersion` | 是 | 回执模式版本 |
| `receiptId` | 是 | 全局唯一且幂等的结算 ID |
| `experimentId` | 是 | 十局实验批次 ID |
| `runIndex` | 是 | 1 至 10 的连续序号 |
| `explorerId` / `identityId` | 是 | 探索者和身份主体 |
| `journeyId` / `regionId` | 是 | 对局和世界切片 |
| `startedAt` / `settledAt` | 是 | 服务端时间 |
| `worldTimeBefore` / `worldTimeAfter` | 是 | canonical 世界时间 |
| `seed` | 是 | 可重放随机种子 |
| `rulesetVersion` | 是 | 数值规则版本 |
| `catalogVersion` | 是 | 内容目录版本 |
| `scenarioTags` | 是 | 强度、适配、路线和目标标签 |
| `outcome` | 是 | 成功、失败、撤退或中断 |
| `snapshots.before` | 是 | 开局权威投影及哈希 |
| `snapshots.after` | 是 | 结算后权威投影及哈希 |
| `deltas` | 是 | 由前后投影和事件共同证明的净变化 |
| `score` | 是 | 总分、等级、八维分项和扣分来源 |
| `suitability` | 是 | 十维需求、角色向量和匹配结果 |
| `rag` | 是 | 记忆写入、摘要、负载和来源事件 |
| `world` | 是 | 世界变化或合法无变化原因 |
| `eventIds` | 是 | 本局全部 canonical event ID |
| `integrity` | 是 | 回执哈希、事件范围和重放校验信息 |

### 6.1 玩家前后快照

玩家快照必须包含以下域，即使某域本局没有变化也不能省略：

- 身份等级、传承等级和当前阶段。
- 六项基础属性及所有派生值。
- 十维战斗适配向量。
- 修行体系、功法、境界、瓶颈和修行资源。
- 天赋、技能树节点、技能等级和技能进阶材料。
- 伤势、负面状态、疲劳、压力和恢复状态。
- 随身物品格、局外仓库、已部署装备和保险状态。
- 货币、通用材料、专属材料、装备和任务物品。
- 铸造、缝纫及其他生产专业的等级、配方和队列。

### 6.2 `deltas` 规则

每一个非零变化必须包含：

- `path`：被改变的稳定字段路径。
- `before` 和 `after`：前后数值或集合摘要。
- `delta`：数值差、增加项和移除项。
- `reasonCode`：稳定原因码。
- `eventIds`：导致变化的 canonical event。
- `source`：战利品、消费、制作、任务、修行、交易、损耗或恢复。

零变化不能伪造为成长。对关键域没有变化时，回执必须提供稳定的 `noChangeReason`，例如“未获得对应材料”“未满足突破条件”“本局没有重要新记忆”。

### 6.3 仓库与经济守恒

每局经济变化必须满足：

```text
期末持有 = 期初持有 + 掉落 + 奖励 + 交易流入 + 制作产出
         - 消耗 - 交易流出 - 制作投入 - 损耗 - 丢弃
```

系统性铸币、系统性销毁和手续费必须使用独立原因码，不能混入普通掉落或消费。任意资源的无法解释差额必须使该局失败。

### 6.4 成长与修行

成长回执必须区分：

- 基础属性永久成长。
- 局内临时增益。
- 装备和功法带来的派生增益。
- 技能熟练度和技能点。
- 修行进度、瓶颈和突破。
- 天赋解锁、重置和分支锁定。

任何永久成长都必须同时满足规则条件、成本消耗、事件写入和上限约束。任务强度只能影响风险、奖励池和需求向量，不能直接映射为某个基础属性增长。

### 6.5 RAG 投影

RAG 回执必须包含：

- 本局新产生的重要记忆，数量范围 0 至 3。
- 被更新、压缩或失效的记忆。
- 新颖度、记忆负载和可追溯性变化。
- 每一条记忆对应的 canonical event ID。
- 没有持久记忆变化时的明确原因。

普通节点默认不改变持久 RAG 面板。RAG 变化不能反向生成资源、属性、技能或世界事件。

### 6.6 世界切片

世界回执只记录与该局可见或因该局直接、间接触发的变化，包括阵营、人物、地点、供应、危险、传闻、物流和时间。每局必须满足以下两种情况之一：

1. 至少一个世界变化带 canonical event 和前后值。
2. 提供 `noWorldChangeReason`，证明本局时间跨度和动作没有跨过任何世界演进阈值。

## 7. 评分、适配度与强度

### 7.1 八维任务评分

任务评分继续使用既有八维框架：目标完成、资源效率、风险控制、信息质量、路线执行、战术质量、撤离质量和附加目标。每个分项必须有输入值、权重、得分和原因码。

评分不得读取基础属性总和、装备总价、身份等级、单一战斗力或任务强度标签。高强度任务不自动高分，低强度任务也不自动低分。

### 7.2 十维适配度

遭遇结算读取角色十维能力向量与场景十维需求向量。适配度影响成功概率、资源消耗、伤势概率、可选路线和撤退难度，但不直接加到任务评分。

### 7.3 数值验收关系

必须同时证明：

- 在相同决策质量下，更高适配度显著提高成功率或降低代价。
- 在相同适配度下，更好决策显著提高任务评分。
- 任务评分与任务强度的绝对相关系数小于 `0.15`。
- 不同构筑在各自擅长场景中有优势，不存在单一向量支配全部场景。
- 十局烟雾验收中，评分分项不同的局不能全部得到同一个总分。

十局用于真实链路验收，`10,000` 局用于快速统计门禁，`100,000` 局用于发布前平衡门禁。

## 8. 十局实验协议

### 8.1 实验前固定项

- 生成唯一 `experimentId`。
- 记录代码版本、规则版本、目录版本和数据库迁移版本。
- 使用一个明确的测试身份，保存完整初始快照和哈希。
- 固定十局场景矩阵和种子，但不固定模型的合法动作选择。
- 清空本实验日志，不清空 canonical 历史。
- 验证公开 MCP surface 不含任何旧版 `agent_world.*` 工具。

### 8.2 每局流程

1. 读取并保存 `player_panel`、仓库、成长、RAG 和世界切片的开局快照。
2. 调用正式 `start_journey`，不得通过内部接口伪造旅程。
3. 只使用服务端签发或服务端校验的动作推进。
4. 结束后提交幂等结算并生成 `RunReceipt`。
5. 读取正式结果页，不得从模型自然语言中提取结算值。
6. 再次读取五类投影并校验回执中的前后哈希和差值。
7. 将 MCP 调用、事件范围、结果页和回执关联到同一 `runIndex`。
8. 任一步骤出现内部错误、缺字段、无法解释差额或投影不一致，本局标记失败并保留证据。

### 8.3 十局场景矩阵

| 局次 | 强度 | 适配状态 | 主要目标 | 预期覆盖 |
|---:|---|---|---|---|
| 1 | 低 | 充分准备 | 资源获取 | 基础仓库流入 |
| 2 | 低 | 准备不足 | 信息获取 | 低风险失败或保守撤退 |
| 3 | 中 | 充分准备 | 战术达成 | 技能与消耗品使用 |
| 4 | 中 | 临界准备 | 护送或保护 | 意志、压力和路线选择 |
| 5 | 中 | 构筑错配 | 资源保全 | 适配度惩罚但评分可解释 |
| 6 | 高 | 充分准备 | 高价值目标 | 高风险高成本成功 |
| 7 | 高 | 准备不足 | 生存撤离 | 失败、伤势和保险 |
| 8 | 中 | 充分准备 | 修行材料 | 修行进度或明确无突破原因 |
| 9 | 中 | 专业构筑 | 制作材料 | 铸造或缝纫输入链 |
| 10 | 动态 | 混合准备 | 重复路线 | 世界记忆、RAG 去重和反刷 |

矩阵描述的是验收覆盖，不允许写死结果。模型仍然可以做出不同合法选择，服务端必须记录实际路径。

### 8.4 实验后汇总

十局报告必须输出：

- 成功、失败、撤退和中断数量。
- 每局总分、八维分项、强度和适配度。
- 所有货币、材料、装备和任务物品的总流入、总流出和净变化。
- 所有基础属性、技能、天赋、修行、伤势和局外容量变化。
- RAG 新增、更新、压缩、去重和无变化数量。
- 世界事件数量、世界时间跨度和无变化原因。
- MCP 错误、内部错误、重试、重复提交和旧版工具调用。
- 每个异常关联的 `receiptId`、`eventIds` 和证据路径。

## 10. 进度权威规则

### 10.1 单一权威源

`.omx/state/phase-6-observable-ten-run-progress.json` 是 Phase 6 当前状态的唯一权威源。规格和 checklist 定义“要做什么”，账本记录“现在做到哪里”。

不得在 README、聊天消息或其他文档中维护独立百分比。需要当前进度时必须运行：

```bash
cd tools/graph-react-app
PHASE6_ATTESTATION_KEY_FILE=/absolute/path/outside-the-repository/phase6-attestation.key \
  npm run agent:phase6-progress -- --markdown
```

机器消费使用：

```bash
cd tools/graph-react-app
PHASE6_ATTESTATION_KEY_FILE=/absolute/path/outside-the-repository/phase6-attestation.key \
  npm run agent:phase6-progress -- --json
```

### 10.2 工作项状态

| 状态 | 定义 | 是否计入实现进度 | 是否计入验证进度 |
|---|---|---:|---:|
| `pending` | 尚未开始 | 否 | 否 |
| `in_progress` | 正在实现，尚未形成完整产物 | 否 | 否 |
| `implemented` | 产物存在，但尚未取得足够验证证据 | 是 | 否 |
| `verified` | 验收条件全部满足且证据有效 | 是 | 是 |
| `blocked` | 有明确阻塞原因 | 否 | 否 |

对外报告的“完成度”默认指验证进度，而不是实现进度。实现进度只能用于描述工作已落地但尚未验证的部分。

### 10.3 证据要求

`implemented` 至少需要一个存在于仓库中的产物证据。

`verified` 必须至少包含一种强证据：成功命令及退出码、带 SHA-256 的不可变产物、带来源文件的统计指标。代码审阅意见不能单独把工作项提升为 `verified`。

证据必须记录观察时间、摘要和对应路径。失败输出必须保留，不得只记录成功摘要。

### 10.4 百分比算法

```text
实现进度 = status in {implemented, verified} 的工作项权重之和
验证进度 = status == verified 的工作项权重之和
```

账本不存储派生百分比，报告器每次重新计算。里程碑权重、工作项权重、规格标记、checklist 标记或勾选状态不一致时，报告器必须非零退出。

## 11. 发布验收门禁

### 11.1 真实链路门禁

- 十局全部生成合法 `RunReceipt` 和正式结果页。
- 十局全部可以关联到开局快照、结算快照和 canonical event 范围。
- MCP `internal_error` 为 0，旧版工具调用为 0，重复结算为 0。
- 注册调用幂等且身份归属稳定。
- 任一关键面板读取失败都会被实验判为失败。

### 11.2 数值门禁

- 所有资源的不可解释守恒差额为 0。
- 不存在负库存、重复奖励、无限铸币和死物流。
- 永久属性成长全部拥有规则、成本、上限和事件来源。
- 任务强度不会自动增加智力、意志或体魄。
- 十局中不同评分分项不会被压平成固定总分。
- `10,000` 局评分与强度绝对相关系数小于 `0.15`。
- `100,000` 局发布模拟满足既有经济、成长和构筑多样性门禁。

### 11.3 RAG 门禁

- 最近关键事实召回率不低于 `95%`。
- 路线摘要精度不低于 `90%`。
- 所有持久记忆可追溯到 canonical event。
- 不存在 RAG 覆盖权威状态的写入路径。
- 普通节点不会制造无意义的持久记忆膨胀。

### 11.4 世界门禁

- 世界时间只由服务端推进。
- 十局跨越的世界时间与触发的宏观 tick 可以重放。
- 每局有世界变化或合法无变化原因。
- 同一 seed、规则版本和动作序列产生相同 canonical event 结果。

### 11.5 进度门禁

- 所有 40 个工作项均为 `verified`。
- 报告器严格校验通过，验证进度为 `100%`。
- checklist 中只有 `verified` 工作项被勾选。
- 不存在未记录 blocker、失效证据或指向仓库外部的证据路径。

## 12. 实施顺序

1. 先完成 `P6-M1` 和 `P6-M2`，建立稳定回执和前后快照。
2. 并行完成 `P6-M3`、`P6-M4`、`P6-M5`、`P6-M6` 的投影差值和事件来源。
3. 完成 `P6-M7`，让结果页成为正式验收入口。

5. 完成 `P6-M9` 的真实十局验收器并产出不可变证据包。
6. 使用 `P6-M10` 报告器核对规格、checklist、证据和最终进度。

## 13. Definition of Done

Phase 6 只有在以下条件同时满足时才算完成：

- 进度报告器输出 `verifiedPercent: 100`。
- 十局真实 MCP 链路报告通过全部真实链路门禁。
- `10,000` 局快速模拟和 `100,000` 局发布模拟通过对应数值门禁。
- 资源、成长、RAG、世界和评分均可从结果页追溯到 canonical event。
- 不存在已知内部错误、旧版入口、默认值掩盖或无法解释的数值变化。
- 失败场景、撤退场景、重复提交和重放场景均有证据。
- 规格、checklist 和机器账本中的 ID 与权重完全一致。

“十局跑完”“命令退出 0”“模型说成功”或“代码已存在”都不是单独成立的完成条件。
